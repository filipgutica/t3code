# Workbench upstream catalog

The intended end state is thin Workbench integration points and direct reuse of native T3 Code, with no copied implementations or fork-only changes to native behavior. This catalog records the exceptions so maintainers can retire them as soon as native capabilities fit. Each exception states its reason and removal condition. [Upstream first](workbench-fork.md#upstream-first) sets the rules; an existing exception does not authorize another one.

Before adding an exception, record it in the same PR. A copy of native behavior also needs maintainer sign-off. During upstream sync, check the removal conditions against new native capabilities. The goal is to run Workbench as a T3 Code extension.

**Status:** _Recorded_ documents an existing change, not approval to retain it indefinitely. _Debt_ identifies a removal candidate that does not need a new upstream capability, subject to caller verification. The Workbench maintainer owns retirement. Integration hooks are listed separately from changes to native behavior and duplicated implementations.

## Baseline and coverage

The baseline is product commit `3c652eba1040b6cf198e6697f52277f8bd20ea31`, compared with integrated upstream `570d4b03eef879bd60be3d74444046858c94dacd`. `node scripts/workbench-isolation.ts --report` reports 203 paths outside the fork boundary: 135 upstream-owned paths, 67 fork-added paths, and one generated lockfile. Deleted workflow paths count separately from their archived destinations.

The purpose rows below group the report paths, including tests, deleted workflows, and fork-added support files. The baseline audit checked all 203 paths against these purposes; the generated report remains the exhaustive path list. A file can serve several purposes: notably `ChatView.tsx` also carries planning controls and cross-environment PR handling, and `Orchestrator.ts` also carries repository binding. The [isolation policy](../../scripts/workbench-isolation-policy.json) separately records exact runtime import allowances; it does not cover all native patches.

The inventory changes only this fork-owned document. Existing upstream sites receive no new comments. Add a purpose/removal comment when a later implementation changes a site, as required by upstream-first guidance.

## Adding or retiring an entry

Add a purpose row in the PR that introduces the exception. Name the native capability that would remove it. Add the short purpose/removal comment at each new or changed upstream site; do not bulk-annotate untouched baseline sites. A Workbench copy also names its native equivalent and needs sign-off before implementation.

When an exception is removed, delete its purpose/copy row if no sites remain. Use a fresh isolation report to check current paths; keep this catalog focused on reasons and removal conditions.
