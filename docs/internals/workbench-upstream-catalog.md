# Workbench upstream catalog

This catalog records every place where Workbench does not simply reuse upstream T3 Code: changes to upstream-owned files, and Workbench copies of native behavior. Each entry says why upstream can't own it today and what upstream capability would let us remove it. [Upstream first](workbench-fork.md#upstream-first) sets the rules.

Use it in three ways:

- **Before you add an exception:** add its entry in the same PR. A Workbench copy also needs maintainer sign-off first.
- **During an upstream sync:** check whether the sync brings a capability that an entry waits for. If it does, plan a follow-up PR that switches to it and removes the entry.
- **Toward an extension:** the "Remove when" column is the list of extension capabilities Workbench needs from T3 Code.

The catalog explains why; it doesn't list files. For the exhaustive list of changed upstream-owned paths, run `node scripts/workbench-isolation.ts --report`. For the upstream files that import Workbench code, with a reason for each, read [the isolation policy](../../scripts/workbench-isolation-policy.json).

**Status:** _Recorded_ means the reason is documented and the change was approved by merge. _Pending_ means the change merged before this catalog existed and still needs its reason and removal condition written down.

## Adding an entry

Add a row in the PR that introduces the exception. State the purpose, not the file list, unless the sites are few. Name the upstream capability in "Remove when" as precisely as you can, so a reader of upstream release notes can recognize it.

At each new or changed site in an upstream-owned file, add one short comment that names the purpose and the removal condition, such as `// Workbench: register the Ticket routes. Remove when T3 Code supports route extensions.` A Workbench copy carries the same kind of comment naming its native equivalent.

When you remove an exception, delete its row in the same PR.
