# Jira sprint mirrors

A Jira binding connects one Workbench Workspace to one Jira board and one or more selected sprints. It uses an accessible-site connection, but the Jira project chosen during board discovery does not filter imported issues. Workbench imports only issues assigned to the connected Jira user in the selected board sprints. The binding also holds default repository scope for new Tickets and the rules for translating Jira statuses to Workbench progress. See the [binding schema](../../packages/workbench/src/WorkbenchSchema.ts), [binding service](../../packages/workbench/src/jira/WorkbenchJiraService.ts), and [Jira issue query](../../packages/workbench/src/jira/JiraApi.ts).

## Field ownership

| Owner                   | Fields and records                                                                                                                                                                                                  | Write boundary                                                                                                                                                                    |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Jira                    | Imported Ticket summary, description, issue type, Epic, flagged state, sprint membership, rank, and workflow status. The description becomes Ticket Markdown and part of the context attached to a Thread composer. | Sync projects remote changes locally. Description and progress edits use a dedicated Jira command that writes remotely, reads the result back, then updates the local projection. |
| Workbench and native T3 | Ticket repository scope, Ticket Workspaces, Assignments, native Threads, and their history.                                                                                                                         | Sync preserves these records. The general Ticket update path cannot replace Jira-owned fields. Starting an Assignment does not itself advance Jira status.                        |

The [importer](../../packages/workbench/src/jira/JiraTicketImporter.ts) updates Jira-owned Ticket and Epic fields. The [store](../../packages/workbench/src/WorkbenchStore.ts) guards ordinary edits, while the [Jira write service](../../packages/workbench/src/jira/JiraTicketWriteService.ts) handles remote edits. The [client context builder](../../apps/web/src/workbench/workbench.logic.ts) includes Ticket Markdown. OAuth modes and credential storage are described separately in [Jira OAuth credential custody](workbench-jira-oauth.md).

## Sprint and board selection

`selectedSprints` is the binding's selection; older bindings fall back to `sprintId` and `sprintName`. Those compatibility fields track the first selected sprint. Sync reads each selected sprint and deduplicates issues by Jira issue ID. In `mapped` mode, the binding holds explicit status mappings, so an unmapped incoming status stops the sync. In `mirror_jira` mode, sync refreshes the board's columns and derives progress mappings from their statuses. Canonical `todo`, `in_progress`, and `done` progress remains available for local Tickets and Epic completion. See the [sync service](../../packages/workbench/src/jira/JiraSyncService.ts) and [board projection](../../apps/web/src/workbench/WorkbenchTicketBoard.tsx).

Bindings follow active sprints by default. Sync retains selected sprints that remain active and replaces closed selections only when the newly active candidate set gives an unambiguous replacement for each missing sprint. `observedActiveSprintIds` excludes parallel sprints that were already running. If an older binding has no observation history, or replacement is missing or ambiguous, sync reports an error and preserves the last successful projection. A pinned binding keeps its selected sprints. See the [rollover logic](../../packages/workbench/src/jira/JiraSyncService.ts).

## Reconciliation boundary

Manual sync, foreground refresh while a Workbench page is visible, and the server's five-minute fallback all use the same binding sync path. A per-binding permit serializes sync, binding edits, and Jira writes. Sync fetches Jira data and validates every incoming status before opening a SQLite transaction. It then updates Ticket and Epic projections, issue links, sprint and board metadata, and sync time together. If the binding changed during the fetch, the transaction rejects the stale result. See [client refresh](../../apps/web/src/workbench/useWorkbenchPageRefresh.ts), [server scheduler](../../packages/workbench/src/jira/WorkbenchJiraService.ts), and [sync transaction](../../packages/workbench/src/jira/JiraSyncService.ts).

Issue links keep a stable local Ticket ID. When an issue leaves the selected sprints, reconciliation marks its link inactive instead of deleting the Ticket or delivery history. Pausing a binding stops its sync and Jira-backed writes without discarding the binding or issue links. Remote Jira edits and local SQLite commits are separate operations: a successful remote write followed by a failed local read or projection requires refresh before retry. See [link reconciliation](../../packages/workbench/src/jira/JiraReconciliation.ts) and [remote write path](../../packages/workbench/src/jira/JiraTicketWriteService.ts).
